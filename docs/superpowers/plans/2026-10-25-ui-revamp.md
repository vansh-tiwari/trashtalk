# TrashTalk UI Revamp Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the current generic dark/glass UI with the proposed light Matchday identity and a clear compare → evidence → commentary → share experience.

**Architecture:** Retain the current app and battle API. Introduce shared semantic tokens, focused form/result/problem/share components, and a presentation adapter for existing snapshots. Design state fixtures keep visual development independent from incomplete backend repairs.

**Tech Stack:** Existing Next.js 15, React, TypeScript, Tailwind, Lucide; locally bundled Barlow/Barlow Condensed; existing Vitest and proposed Playwright visual/browser coverage.

**Spec:** `docs/superpowers/specs/2026-10-25-ui-revamp-design.md` and `design-system/trashtalk/MASTER.md`.

**Status:** Proposed plan. Matchday and exact tokens are designer recommendations, not an approved implementation. This turn installs the requested skill and writes planning artifacts only.

## Global Constraints

- The user wants a new lighter identity, not a restoration of the legacy appearance.
- No application implementation is included in this planning turn.
- Do not edit `legacy/` or disturb the existing staged migration and other working changes.
- Light theme is the primary and only new theme in this pass.
- Keep Next.js/React/Tailwind/Lucide and existing battle routes.
- Color never carries winner/player/availability meaning alone.
- The presentation adapter must expose unknown data honestly instead of hiding backend failures.
- No new providers, leaderboard, authentication, billing, social feed, or automatic publishing is part of this UI revamp.

## Review Focus

1. Long/dotted handles, long tags, and 200% text zoom must preserve readable comparisons and operable controls (Tasks 2–4).
2. Missing fields, unsupported old snapshots, partial evidence, and null winners must never become false zeros or a fabricated victor (Task 3).
3. Invalid/slow/busy/failed submissions must retain inputs and explain the state with correct focus/status behavior (Task 2).
4. Mobile menus, share popovers, and filters must remain keyboard/touch accessible with focus restoration (Tasks 2, 4, 5).
5. All three image aspect ratios and reduced-motion/phone layouts require actual visual inspection, not only byte/dimension tests (Tasks 1, 5, 6).

## Task 1: prove the visual direction before broad implementation

- [ ] Create a high-fidelity home and saved-result design at 1440px and 390px using one consistent Matchday system. Use labeled sample data. Show the form, result, metrics, problems, commentary, and sharing hierarchy rather than only a decorative hero.
- [ ] Include alternate win, draw, and insufficient-data states plus an open export preview; inspect the story composition.
- [ ] Compare the proposed design against the source audit: visible form, aligned values, readable text, distinct hierarchy, and personality without glow/badges/ticker. Review with the user before spreading the design across routes. This checkpoint tests visual taste; do not treat a generic design-system generator output as approval.

**Exit:** Approved home/result direction, desktop/mobile, with settled tokens and hierarchy. No broad production redesign before that visual review.

## Task 2: implement shared foundations and entry flow

**Files:** Global/shell/compare files in the map, home and battle/solo routes; add `tests/e2e/ui/compare.spec.ts`.

**Interfaces:** `CompareForm({initialHandles, initialPersona, mode, onCreated})` owns the existing validated submit flow and preserves retry state. Modes reflect supported battle/mirror behavior only; `onCreated` receives the canonical ID. `MatchStatus` exposes `idle | submitting | busy | error` without inventing backend progress phases.

- [ ] Add browser checks for visible labels, query-prefilled handles, swapping, Enter submission, preserved values after error, retry identity, and correct navigation after success. Include long/dotted handles, 200% zoom, and keyboard focus.
- [ ] Introduce the master tokens, local fonts, responsive gutters and quiet shell. Remove forced-dark classes and hardcoded legacy-modern dark surfaces from migrated components; avoid accidental mixed themes.
- [ ] Replace repeated forms with the shared component and implement the new compact home. Move the architecture pitch to the story page; remove the perpetual ticker and misleading instant-match labels.
- [ ] Test 375/390/768/1440px and reduced motion; preserve 44px controls and meaningful loading/errors. Compare screenshots to the approved checkpoint.

**Exit:** One consistent light entry experience across routes with working existing behavior and no form regressions.

## Task 3: rebuild saved results around the scoreboard

**Files:** `src/lib/battle/presentation.ts`, new battle components, saved-result route, existing radar; add `tests/unit/battle/presentation.test.ts` and `tests/e2e/ui/result.spec.ts`.

**Interfaces:** `toBattleViewModel(snapshot)` preserves the persisted win/draw/insufficient outcome and adds `evidenceState: 'supported' | 'partial' | 'unknown'`. Each displayed metric is either `{kind:'value', value, label, scope}` or `{kind:'unavailable', reason}`. Preserve player IDs/orientation and separate source/freshness metadata. Do not recompute or change the stored outcome. For unknown/partial coverage, follow the spec's explicit **Recorded result / Recorded score** policy, with its prominent warning and no authoritative winner stamp. `Scoreboard` and all exports consume this presentation policy consistently.

- [ ] Add fixture tests for win/draw/insufficient, old snapshots, partial/unknown coverage, null winner, missing URL/avatar, and long handles. Assert unknown/partial evidence preserves the underlying recorded verdict, labels it as unvalidated, adds the specified warning, and omits an authoritative winner stamp. Assert no `@null`, `@undefined`, unsupported lifetime labels, or invented zeros.
- [ ] Build compact identity/outcome headers, aligned three-column metric rows, “Why this result?” disclosure, and one short commentary line. Keep both player values visible together on phones.
- [ ] Place detailed radar/numerical skills view and fuller persona commentary after the primary evidence sections. Keep commentary source and data context legible in plain language.
- [ ] Verify direct saved-link/reload/back behavior, 200% zoom, metric/header semantics, and clear outcome states across desktop/mobile fixtures.

**Exit:** A visitor can immediately identify the matchup/outcome and compare raw values without traversing separate decorated cards.

## Task 4: make problem exploration a first-class tool

**Files:** New problem explorer/table/filter components; replace `ProblemOverlapArena.tsx` usage after the new surface works. Add `tests/e2e/ui/problems.spec.ts`.

**Interfaces:** `ProblemExplorer({overlap, player1, player2, coverage})` uses stable problem IDs. Search is by name/ID; rating filters use the platform's native rating; default sort is rating descending with stable ID tie-break and unrated last. Partial/unknown exclusives show an unavailable explanation rather than zero solved.

- [ ] Add checks for tab keyboard navigation/state, search, rating/sort, no results, unrated items, long names/tags, missing URLs, and partial evidence. Assert enabled statement links have valid provider URLs and remain present after loading a saved battle.
- [ ] Implement the compact semantic table/list with usable controls, counts, empty states and metadata disclosure. Keep search/filter state when changing tabs where applicable; announce meaningful result counts without moving focus.
- [ ] Test a long problem set with pagination or incremental rendering, preserving full comparison counts. On phones, keep essential name/rating/link readable with optional metadata disclosure and no page-wide overflow.

**Exit:** Problem comparison is searchable, scannable, and reliable on mobile; the UI does not conceal missing backend URL/coverage fixes.

- [ ] Recompose OG/story/square cards using local shared fonts and tokens. Include outcome, handles, short punchline, canonical URL, timestamp, and sample/coverage context. Give story cards non-collapsing geometry; test long text and all outcome states.
- [ ] Build The story with real origin/source comparisons and honest engineering claims; apply the same shell to solo without presenting a mirror match as a dedicated analysis engine.
- [ ] Complete invalid, missing, busy, partial, insufficient, persistence-failed, removed-result and export-failed surfaces. Use fresh state fixtures; never rely exclusively on the prepared success demo.
- [ ] Render and inspect all actual images and desktop/phone pages. Export tests must consume PNG bodies and check dimensions plus visual content/layout.

**Exit:** Every public surface and shared artifact belongs to one intentional design, including error states.

## Task 6: verify the whole experience and remove obsolete styling

- [ ] Run critical browser journeys with mocked boundary responses and a blocked-network test mode: form → saved result → problem link/filter → share/export → rematch, plus all defined failures. Then run a real preview with the completed backend fixes.
- [ ] Check 375/390/768/1024/1440px, 200% zoom, keyboard-only flow, visible focus, reduced motion, contrast, full handles, and image fallback. Save review screenshots of representative pages/states and all three exports.
- [ ] Remove unused glass/gradient/pulse helpers and obsolete components only after references are migrated. Do not delete domain/provider code as part of a style cleanup.
- [ ] Run actual configured lint, typecheck, relevant tests, browser/visual checks, and isolated production build. The existing typecheck-as-lint shortcut does not satisfy the lint check.
- [ ] Record what changed, verification evidence, and remaining backend/deployment blockers. Do not claim public readiness until the separate readiness closure items are complete.

**Exit:** Approved design implemented consistently and verified through real user-visible flows. Deployment remains a separately authorized step.

## Suggested execution

Approve one home/result desktop/mobile checkpoint, then implement foundations → result hierarchy → problem explorer → exports/story/states → regression review. Backend correctness can progress independently; no new platform work is needed for this visual revamp. The old launch-readiness plan remains a release dependency, not a reason to postpone the design.
